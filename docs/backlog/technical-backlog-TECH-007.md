# Technical Backlog — TECH-007

## TECH-007 — Definir convenções de persistência JPA/Hibernate

### Objetivo

Estabelecer a infraestrutura e as convenções oficiais de persistência do backend usando JPA/Hibernate sobre PostgreSQL, sem implementar ainda entidades de negócio completas.

Esta TECH prepara o projeto para as próximas migrations, entidades de persistência e repository adapters.

### Escopo incluído

- adicionar JPA/Hibernate via Spring Boot starter apropriado;
- configurar Hibernate apenas para validação do schema;
- garantir que Flyway continue sendo o único mecanismo de evolução do schema;
- estabelecer convenções de IDs;
- estabelecer convenções de enums;
- estabelecer convenções para BigDecimal/money;
- estabelecer convenções para LocalDate e Instant;
- estabelecer convenção para optimistic locking;
- estabelecer separação entre domínio e entidades JPA;
- estabelecer convenções de repository ports/adapters;
- documentar estratégia de auditoria persistente;
- criar somente a infraestrutura mínima necessária para provar que JPA consegue inicializar sobre o schema atual;
- criar testes técnicos mínimos, se necessários.

### JPA/Hibernate

Adicionar:

- Spring Data JPA / Hibernate através do starter oficial do Spring Boot.

Hibernate deve usar:

`ddl-auto=validate`

ou configuração equivalente compatível com a versão atual do Spring Boot.

Nunca utilizar:

- update
- create
- create-drop

Hibernate não possui ownership do schema.

Flyway continua sendo a única ferramenta autorizada a criar ou alterar estruturas no PostgreSQL.

### Separação Domain x Persistence

Domain e entidades JPA devem permanecer separados.

Exemplo conceitual:

```text
domain/
  conta/
    ContaFinanceira.java

infrastructure/
  persistence/
    conta/
      ContaFinanceiraJpaEntity.java
      SpringDataContaFinanceiraRepository.java
      ContaFinanceiraRepositoryAdapter.java
```

Não adicionar annotations JPA ao modelo de domínio.

Não criar `@Entity` dentro de `domain`.

### IDs

Padrão oficial:

PostgreSQL:

`BIGINT GENERATED BY DEFAULT AS IDENTITY`

Java:

`Long`

Não criar UUID como padrão geral sem ADR posterior.

Não criar classe genérica de ID nesta TECH.

### Enums

Enums persistidos:

- `VARCHAR`
- `EnumType.STRING`

Nunca usar:

`EnumType.ORDINAL`

Não introduzir PostgreSQL enum nativo nesta etapa.

### Valores monetários

Java:

`BigDecimal`

PostgreSQL:

`NUMERIC(19,2)`

Não usar:

- float
- double

para valores monetários.

### Datas

Datas de negócio:

- Java `LocalDate`
- PostgreSQL `DATE`

Eventos/auditoria/timestamps técnicos:

- Java `Instant`
- PostgreSQL `TIMESTAMPTZ`

Evitar `LocalDateTime` para timestamps que representam instante global.

### Optimistic locking

Entidades que futuramente necessitem proteção contra concorrência poderão usar:

`@Version`

A convenção oficial deve ser documentada.

Esta TECH não deve adicionar `@Version` indiscriminadamente a entidades inexistentes.

### Auditoria

A TECH deve definir como campos técnicos de auditoria serão representados, sem criar um `BaseEntity` genérico.

Exemplos conceituais:

- criadoEm
- alteradoEm

Não criar automaticamente:
- criadoPor
- alteradoPor

se dependerem da autenticação externa ainda não definida.

Evitar `@MappedSuperclass BaseEntity` especulativa.

Preferir composição ou campos explícitos quando entidades reais forem implementadas.

### Repositories

Domain/Application expõem ports quando necessário.

Infrastructure implementa os ports.

Spring Data interfaces pertencem à Infrastructure.

Exemplo:

```text
domain/application port
        ↓
ContaFinanceiraRepository
        ↓
infrastructure adapter
        ↓
SpringDataContaFinanceiraRepository
```

Não expor `JpaRepository` diretamente para Application/Domain.

### Naming PostgreSQL

Identificadores continuam em camelCase.

Exemplos:

- `"contaFinanceira"`
- `"empresaId"`
- `"dataVencimento"`

Não permitir que uma naming strategy converta automaticamente identificadores para snake_case.

O Plan deve verificar o comportamento padrão do Hibernate/Spring Boot atual e propor a configuração mínima necessária para preservar os nomes definidos explicitamente nas annotations/migrations.

### Schema validation

Como a única migration atual é técnica (`V1__flyway_bootstrap.sql`) e não existe entidade de negócio ainda, o Plan deve avaliar como provar a inicialização JPA sem criar uma entidade/tabela artificial.

Preferência:

- não criar tabela fake apenas para TECH-007;
- não criar entidade de domínio antecipadamente.

Se não houver nada a validar ainda, documentar a limitação e garantir que a configuração ficará pronta para as próximas entities/migrations.

### Testes

Os testes herméticos devem continuar sem exigir banco.

Integration tests existentes com PostgreSQL Testcontainers devem continuar funcionando.

Se JPA exigir contexto de banco para validação, isso deve ocorrer somente em integration tests.

Não transformar `mvn test` em dependente de Docker.
