We are planning:

TECH-007 — Define JPA/Hibernate persistence conventions.

Before proposing changes, read:

- docs/architecture/persistence.md

Inspect the current backend after TECH-006.

Do not modify files yet.

Goal:
Prepare JPA/Hibernate persistence infrastructure and establish the conventions that future persistence entities and repository adapters must follow.

Important:
This task does NOT implement business entities or business tables.

Scope:
- add the appropriate Spring Boot JPA dependency;
- configure Hibernate for schema validation only;
- preserve Flyway as the sole schema evolution mechanism;
- establish persistence conventions for IDs, enums, money, dates and timestamps;
- establish optimistic-locking convention;
- establish Domain/JPA separation;
- establish repository port/adapter convention;
- establish technical-audit-field convention;
- verify camelCase PostgreSQL naming behavior;
- preserve hermetic tests and existing Testcontainers integration tests.

Required conventions:

IDs:
- Java Long
- PostgreSQL BIGINT GENERATED BY DEFAULT AS IDENTITY

Enums:
- VARCHAR
- EnumType.STRING
- never ORDINAL

Money:
- Java BigDecimal
- PostgreSQL NUMERIC(19,2)

Business dates:
- Java LocalDate
- PostgreSQL DATE

Technical/event timestamps:
- Java Instant
- PostgreSQL TIMESTAMPTZ

Schema:
- Flyway owns schema evolution
- Hibernate must not create/update schema
- use ddl-auto=validate or the safest equivalent supported by the current Spring Boot version

Architecture:
- Domain must not contain JPA annotations
- JPA entities belong to Infrastructure
- Spring Data repositories belong to Infrastructure
- Application/Domain must not depend on JpaRepository

Important naming requirement:
The database uses camelCase identifiers.

Do not allow a Hibernate naming strategy to silently transform explicitly defined database names into snake_case.

Analyze the current Spring Boot 4.1.1 / Hibernate behavior and propose the minimum configuration necessary.

Important schema-validation question:
Currently the only migration is the technical V1 Flyway bootstrap and there are no business entities.

Do NOT create a fake table/entity merely to prove Hibernate works.

Analyze what can be validated now and document what will only become meaningful when the first real entity/migration is introduced.

Testing:
- `mvn test` must remain Docker-free;
- persistence/JPA validation that requires PostgreSQL belongs in integration tests;
- existing PostgreSQL 16 Testcontainers infrastructure must be reused;
- do not add H2.

Explicitly out of scope:
- Empresa entity/table;
- Filial entity/table;
- Parceiro entity/table;
- ContaFinanceira entity/table;
- Parcela;
- MovimentacaoFinanceira;
- business repositories;
- CRUD;
- REST endpoints;
- authentication;
- authorization;
- Kafka;
- business migrations;
- user-based auditing;
- financial idempotency.

Do not introduce:
- BaseEntity;
- BaseRepository;
- GenericRepository;
- generic CRUD abstractions;
- JPA annotations in Domain;
- snake_case;
- EnumType.ORDINAL;
- Hibernate schema creation/update.

Create a plan containing:

1. Current-state analysis
   - current dependencies;
   - datasource/Flyway setup;
   - test profiles;
   - Testcontainers setup;
   - package structure.

2. Dependency changes
   - exact dependency;
   - version-management strategy;
   - transitive Hibernate implications.

3. Hibernate/schema configuration
   - exact properties;
   - profiles affected;
   - explain how Flyway remains owner.

4. Database naming strategy
   - analyze Spring Boot/Hibernate defaults;
   - explain how camelCase will be preserved;
   - avoid unnecessary custom naming strategy if explicit annotation names are sufficient.

5. Persistence conventions
   - IDs;
   - enums;
   - money;
   - dates;
   - timestamps;
   - nullability;
   - relationships;
   - lazy/eager defaults where relevant.

6. Domain vs persistence model
   - package boundaries;
   - mapping responsibility;
   - repository port/adapter structure.

7. Optimistic locking convention
   - when @Version should be used;
   - where it belongs;
   - do not add it to nonexistent entities.

8. Audit convention
   - created/updated timestamps;
   - avoid BaseEntity;
   - do not add user auditing before external auth exists.

9. Test strategy
   - preserve hermetic unit tests;
   - integration-test implications;
   - determine whether existing FlywayMigrationIT needs adjustment;
   - do not create fake business schema.

10. Files
   - exact files expected to create;
   - exact files expected to modify.

11. Validation commands
   - mvn test;
   - mvn package;
   - mvn verify when Docker is available.

12. Scope compliance
   Confirm explicitly:
   - no business entity;
   - no business table;
   - no business repository;
   - no REST endpoint;
   - no auth;
   - no Kafka.

13. Risks and assumptions
   - Hibernate 7/Spring Boot 4.1.1 behavior;
   - camelCase naming;
   - ddl-auto validate with zero mapped entities;
   - Testcontainers context behavior;
   - documentation conflicts.

Prefer the minimum infrastructure and documentation necessary for future persistence work.

Do not implement yet.
